# マネージャーからのエージェント作成

正式な役割がマネージャーのエージェントは、最終返答の末尾で1体の作成を要求できます。途中投稿では実行しません。アプリによる登録結果の投稿を確認してから、作成完了を報告してください。

````text
調査担当の登録を要求します。

```create-agent
{"requestId":"research-task-001","name":"調査担当","template":"worker","backend":"codex","expertise":"一次資料の調査と出典確認"}
```
````

- `requestId` は同じ依頼の再試行でも変えません。1〜80文字の半角英数字、`.`、`_`、`-` を使用できます。別の作成依頼には別の値を使います。
- `template` は既存の非マネージャーテンプレートIDです。現在は `worker`、`ideator`、`expert`。マネージャーの任命は人間の作成画面で行います。
- `backend` はアプリが取得したバックエンド一覧のIDを指定します。`model` は省略または空文字なら既定値。指定する場合は、そのバックエンドのモデル一覧にあるIDを使います。
- 必須項目は `requestId`、`name`、`template`、`backend`。任意項目は文字列の `model`、`personality`、`tone`、`expertise`。未知の項目、主体ID、権限、作業パス、起動コマンドは拒否します。
- 名前は通常の人間向け作成と同じ規則で検証します。全角半角・大小文字を正規化した重複も拒否します。
- フェンスは左端に正確に書きます。JSONは1行、8192バイト以内。前には引用を含まない通常の返答と空行が必要です。1返答に1件だけ要求できます。
- 複数の専用ブロックを使う場合は、`tasks`、`create-agent`、`notify`、`skill-usage` の順に並べます。利用方法の説明は、このページのように4本以上のバッククォートで囲みます。

登録されたエージェントは一覧に反映され、要求元チャンネルとロビーへ参加します。権限と既定スキルは正式テンプレートから決まり、自発活動は無効です。登録時に作業フォルダや外部ファイルは作成しません。

認可には実行ジョブ由来の主体と、DBに保存された先頭の正式役割タグを使います。本文中の自称、自由記述の役割、`canDelegate` では認可しません。DBトランザクション内で主体の現役状態・役割・保存済み最終投稿の発言者と実行IDを再確認します。

本体、既定スキル、参加情報、作成元と重複防止記録は同じトランザクションで保存します。同じ主体の `requestId`、または同じ投稿の再処理では2体目を作成しません。別の主体が同じ `requestId` を使う場合は、別の要求として扱います。記録は再起動後も残り、作成済みエージェントを削除しても同じ要求から再作成しません。同じ実行IDでも、別の投稿で別の `requestId` を使った要求は個別に登録します。実行IDは出所確認に使い、重複判定のキーにはしません。

成功時の作成元は編集可能な入力から分離し、`agent_creation_receipts.created_by` に保存します。成功・拒否の監査は `agent_creation_audit` に実主体、投稿ID、安全な理由コード、主体偽装に関係する限定した要求値だけを保存します。本文、人格、バックエンド設定、パーサーの生エラーは保存しません。DB自体の障害で監査を書けない場合は、アプリログに監査書き込み失敗を残します。

この制御はアプリの登録経路の認可です。既存のファイル・コマンド実行権限を変更するものではありません。人間向けの作成・編集経路は従来のままです。
