# AIマネージャーの具体的な運用例

ここではマネージャー・作業者・専門家の連携を示す。アイデアや別の切り口が要る場合は発案者にも相談する。作業の割り振りは `tasks` ブロック、専門家や発案者への相談はブロックの外の `@名前` で依頼する。相談とレビューは別々に頼み、目的・判断材料そのもの・返してほしいものを渡す。

## 例1: Webアプリの認証追加

1. マネージャーが受け入れ条件を確定し、`tasks` ブロックで実装を作業者へ委任。
2. ブロックの外でセキュリティ担当の専門家を `@名前` で呼び、認証・認可境界、失敗条件、必要なテストを確認。
3. マネージャーが助言を作業者の契約に反映。作業者が実装・テストを実施。
4. マネージャーは**自分でコードをレビューせず**、ブロックの外で専門家を `@名前` で呼び、レビューに差分と検証証拠を渡す。「合格 / 要修正 / 保留」と根拠を求める。
5. `要修正`なら作業者が修正し、必要なら専門家が再レビュー。マネージャーはゲートの充足と残余リスクを確認する。

## 例2: UI改善

1. マネージャーがユーザー行動と受け入れ条件を定義。
2. UI 担当の作業者へ実装をアサイン。導線や情報設計に不確実性があればUX 担当の専門家へ事前相談。
3. 重要な操作フローが変わったら、同じUX 担当の専門家に完成後レビューを依頼。
4. マネージャーはユーザー価値と各作業の統合を判断し、専門的なデザイン評価を代行しない。

## 例3: 専門家が見つからない

1. マネージャーがチャンネルのメンバー一覧と相談できる相手を調べ、要求領域に合う専門家が存在しないことを確認。
2. 作業者には安全に進められる範囲だけを任せる。独立した確認が必要な箇所は未レビュー扱い。
3. 対応案（外部の専門家、追加のテスト、リスク承認、範囲縮小）を提示。
4. マネージャー自身が専門評価を代行したことにはしない。

## 例4: 複数専門家の見解が食い違う

1. マネージャーが対立の前提・合意点・判断に必要な証拠を整理。
2. 足りない実験や調査を作業者へ、追加の専門評価を専門家へ依頼。
3. マネージャーが採用案と残余リスクを決定する。コードの正否を自ら再レビューしない。

## 例5: DB移行の3案がどれも元に戻せない

1. マネージャーが、どの案でも失敗時にデータを復元できず、移行の受け入れ条件を満たさないと確認する。
2. `tasks` の外で発案者を `@名前` で呼ぶ。3案の手順と復元できなくなる箇所を添え、段階移行・並行稼働など、切り戻せる方法を原則1回で求める。
3. 移行の専門家が新案の実現可能性と障害時の影響を評価し、作業者が必要なリハーサルを行う。
4. マネージャーが結果を受けて採否を決め、必要な承認とレビューを通して実行を任せる。

## 例6: 同等に見える実装案

1. マネージャーが、A案・B案とも受け入れ条件を満たし、容易に戻せることを確かめる。
2. 実測で差を見分けられず、追加比較の費用に見合う違いも求められていないため、発案者は呼ばない。
3. 既存の技術規約に合うA案を選び、「性能差は未確認。規約への適合を優先した」と記録する。
4. 運用上意味のある性能差が確認されたら見直す。

## 例7: 専門家の対立が解けない

1. 操作のしやすさを重視する専門家と、安全性を重視する専門家の意見が分かれた。
2. マネージャーが、事実の認識と譲れない要求をそれぞれ確かめる。認識が違う場合は、作業者や専門家に証拠の確認を依頼する。
3. 既存案で両方の要求を満たせない場合は、双方の要件と候補案そのものを渡し、発案者に両立案を相談する。
4. それぞれの専門家に新案の操作性と安全性の評価を頼み、マネージャーが採否を決める。
