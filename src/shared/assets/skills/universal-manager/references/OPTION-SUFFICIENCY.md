# 選択肢の充足性

重要な決定の前や、着手後に前提が変わったとき、マネージャーが次に誰へ何を頼むかを決めるために使う。

## 今ある案で進めるか

| 確かめること | 進められる例 | 不足がある例 |
|---|---|---|
| 目的と制約を満たす案があるか | 低リスクで実行できる案が1つある | どの案も安全性・品質・費用の最低条件を満たさない |
| 異なる仕組みや失敗のしかたを考慮したか | 1案でも、失敗の影響を限定でき、元に戻せる | 5案とも同じ未確認の前提に依存している |
| 今ある根拠で選べるか、小さく試せるか | 不確かさを承知で選べる、またはすぐ試せる | 実現可能性を左右する事実が分からず、比較できない |

案の数に下限は設けない。失敗の影響、元に戻す手間、探索の時間と費用、期限を踏まえ、追加案で判断が変わりそうかを考える。

## 不足に応じて相談先を選ぶ

- **発案者**には、どの案でも守れない制約、全案に共通する弱点、両立できていない要求を渡し、別の方法を求める。後戻りできない移行なら、並行稼働や段階移行、途中で撤退できる案を相談する。反対意見が出たときは、双方が守りたい条件を渡す。
- **専門家**には妥当性・安全性や問題の原因を相談し、**作業者**には実測・小さな試作を頼む。同じ方法で失敗が続いたら、まず観測した事実と原因の仮説を整理する。方式そのものに限界が見えたら発案者に相談する。
- **マネージャー**は、十分な案がある、影響が小さく戻せる、候補が実質同等と判断できる場合に、選定基準を明らかにして決める。新案も、必要に応じて専門家の評価や作業者の試作を経て採否を決める。

重大・不可逆な決定でも、安全策と根拠がそろっていれば発案者への相談は省ける。反対意見が事実認識の違いから来ていれば、根拠を確かめる。案が1つだけ、複数案が同等に見える、発案者が空いている、といった事情だけで追加案を求めない。

## 発案者への相談の書き方

返答に、`tasks` やコードブロックの外に実在する相手の名前をメンションする。下の項目に沿って、本人が判断できる材料を添える。

- 呼びかけ: `@発案者の名前` に、どの点で別の案が必要かを伝える。
- 目的: 達成したい結果、必ず守る条件、見直してよい前提を示す。
- 判断材料: 候補ごとの仕組み、共通の欠点、満たせなかった条件を示す本文・観測結果・データそのものを添える。
- 返してほしいもの: 仕組みの異なる案、段階的に試して戻せる案、対立する要求を両立する案を、重要なものから最大3件程度。各案で変えた前提、利点、懸念を求める。有力な追加案がなければそう答えてよい。
- 予算と期限: 原則1回でマネージャーに返す。追加の探索で予算や期限を超える場合は、延長するかを決めてから続ける。

## 探索を終える条件

最低条件を満たす案があり、残るリスクを許容できるかを確かめる。そのうえで、追加案が選択を変えそうにない、小さく試す方が安い、または期限や費用から探索を延長する価値が乏しいなら、決定・試作に進む。重大・不可逆な変更では、必要な専門レビューとユーザー承認を確かめる。

1回の相談後も重大な不足が残る場合は、マネージャーが追加探索、条件の見直し、保留、ユーザーへの確認から選ぶ。相談回数や期限に達したことだけで、不十分な案の実行を決めない。

## 同等に見える案を選んだ理由を残す

「性能差はまだ測れていない」と「どちらも必要な性能を満たす」は別の判断である。実績・互換性・切替費用などの確認済みの事実と、将来の変更回数や運用費の予測を分ける。どちらでも条件を満たすなら既存規約や可逆性などで決め、実際に使った基準を記す。

重要な決定では必要な項目を短く残す。

```text
決めたこと: [採用した案]
今決める理由: [期限や次に控える作業]
選択肢: [検討した案、見送った案]
根拠: [確認済みの事実]
仮説・前提: [予測、不確かな点]
選んだ理由: [優先した条件。同等なら採用を決めた規約など]
見直す条件: [判断を変えうる観測結果や状況。不要なら「なし」]
探索判断: [発案者に相談したか、その理由]
```

試さなかった案の結果を「その方がうまくいったはず」と事実のように記録しない。

## 判断例

| 状況 | 次の行動 |
|---|---|
| UI文言の2案はどちらも軽微で戻せる | マネージャーが選ぶ。 |
| 重大なDB移行で、失敗したときに戻す方法が見えない | 発案者に段階移行や切り戻せる案を、移行の専門家にリスクの評価を頼む。 |
| 3案とも同じ箇所の性能に制約される | 発案者に仕組みの異なる案を求める。原因が不確かなら専門家に診断を頼む。 |
| 2方式の性能差が分からない | 作業者が測定し、必要なら専門家が結果を評価する。 |
| 操作のしやすさと安全性の要求が対立する | 専門家に譲れない要件を確認し、既存案で両立できなければ発案者に相談する。 |
| 反対意見が事実の取り違えから生じた | 専門家・作業者に根拠の確認を頼む。 |
| AとBは受け入れ条件を満たし、確認できる差がほぼない | マネージャーが既存規約などの基準で選ぶ。 |
| 作業者が同じ方法で2回失敗した | 記録を集め、必要なら専門家に原因を相談する。前提の見直しが必要なら発案者に別の方法を求める。 |
| 重大な変更だが、安全策と専門家の評価がそろっている | 必要な承認を得て進める。重大さだけで案出しを頼まない。 |

## 運用上の境界

選択肢の充足性はマネージャーが相談先を決める基準である。発案者は必要に応じて `concept-shift` などで案を広げ、専門家はその妥当性を評価する。作業者・専門家も案の不足を申し出てよい。発案者への直接相談は権限・範囲・予算に従う。方針を決めたら、どの前提が変われば探索に戻るかを明らかにする。実行中の方針変更と追加作業はマネージャーが判断する。
