# 専門家へのルーティング例

専門家は1種類で、同一専門家へ相談・レビューの両方を依頼できる。下表は分野選定の例であって、実在しない専門家を仮定してよいという意味ではない。

| 対象タスク | 作業者 | `相談`のタイミング | `レビュー`のタイミング | 典型的な専門家の能力 |
|---|---|---|---|---|
| 認証機能 | 実装担当の作業者 | 認可境界と設計が決まる前 | 実装・テスト完了後 | セキュリティ |
| UI改修 | フロントエンド担当の作業者 | 主要導線の設計前（仕様不明の場合） | 体験が変わる場合に完成後 | UX、アクセシビリティ |
| DB移行 | バックエンド担当の作業者 | 移行・ロールバック方針決定前 | 実行前、必要ならリハーサル後 | データ基盤、SRE |
| 3Dキャラクター | 3D 担当の作業者 | 品質基準・パイプラインで迷うとき | 表現や互換性に重大な影響がある完成時 | 3D、Unity、リギング |
| AI音声パイプライン | 音声担当の作業者 | モデル/レイテンシー方針決定前 | 品質・遅延・失敗処理の評価時 | 音声、リアルタイム推論 |
| 一般文書の軽微な誤字修正 | 文書担当の作業者 | 通常不要 | 必要なら自動/簡易チェックで代替 | — |

## 3つの典型的な失敗

### 1. マネージャーがコードレビューを始めた

- NG: diffを開いてバグ候補の列挙を始める。
- 対処: マネージャーは自分でレビューせず、`tasks` の外で `@名前` を付けて専門家へレビューを頼む。該当ファイルの本文・差分・テスト結果そのものを添え、目的と返してほしいものを渡す。ファイルの場所は出どころを示すために書き添えるだけで、場所の一覧だけでは依頼したことにならない。
- その後: 専門家の`要修正`を作業者へ再委任する。

### 2. 専門家がいるのにアサインしていない

- NG: 担当表に作業者だけ書いて作業開始。
- 対処: `必要能力 → 実在専門家 → 相談/レビューの要否 → 介入タイミング`を作業開始前に決める。
- 専門家不在: 適任の専門家が見つからなければ、レビューは未実施と書いて判断を保留する。マネージャーが自力で専門家を演じない。

### 3. 事前相談と最終評価が混ざる

- NG: 相談した専門家の「この設計でよさそう」を完了後レビューと取り違える。
- 対処: 相談と完成物のレビューは、`tasks` の外で `@名前` を付けて別々に依頼する。レビューは「合格 / 要修正 / 保留」と根拠を求める。
- 同じ専門家が両方を行うことは可能。レビューでは自分の助言の誤りも検討させる。

## 高リスク時の追加ルール

セキュリティ、機密情報、認証/権限、決済、移行・データ消去、本番システムの不可逆変更は、着手前相談と実行前または完成後レビューを原則必須とする。技術レビューだけでユーザーの承認や権限確認を代替しない。
