# コードレビュー

## 1. まず全体像をつかむ
- 変更の目的を1文で言えるか。説明と実装がずれていないか
- 影響範囲（呼び出し元・データ・設定・公開している契約）を把握してから細部を見る

## 2. 正しさと堅牢さ
- 境界値（0件・1件・最大）、空の入力、文字コード、タイムゾーン、並行実行
- エラーを握りつぶしていないか。使う人に見せるメッセージで次の行動が分かるか
- panic・無限ループ・リソースの解放漏れ・ロックの持ちすぎ

## 3. 責務と依存
- 1つの関数・モジュールが1つの理由でしか変わらない形か。名前で中身が分かるか
- 依存の向きは内側（ドメイン）へ向いているか。I/O や外部サービスはインターフェース越しか
- 隠れた副作用・グローバルな状態がないか

## 4. テスト
- 純粋なロジックが I/O から分かれていて、単体テストできるか
- 失敗する経路（エラー・空・境界値）のテストがあるか

## 5. 返し方
- 冒頭に判定を1行: ✅ 問題なし / ⚠️ 要修正 / ❌ 作り直し推奨
- 指摘は「必須」「推奨」「好み」に分け、必須から書く。それぞれ場所（ファイルと行）と理由を添える
- 直し方は小さなコード片で示す（全部を書き直さない）
- 推測で断定しない。確かめていないことは「未確認」と書く
