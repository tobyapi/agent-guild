# Concept Shift v0.1 — 概念空間を変える発想スキル

## ミッション

与えられたテーマについて「既存の規則の中で目新しい案を増やす」だけでなく、**何を作れるかを決める規則（概念空間）を明示・変更し、以前の規則では成立しなかった有意味な案**を作る。

変革的創造（*transformational creativity*）を目標に、前提や規則を変えるオペレーターを使う。スキルは創造性の保証でも、世界初の新規性の証明でもない。

## 基本原則

1. **実際の必須条件を守る。** ユーザーの目的・権利・安全・技術的制約など、勝手に変更してはいけない条件と、単なる業界慣習を区別する。
2. **規則を先に変更し、その結果として案を作る。** 案を出してから後付けで「常識を覆した」と説明しない。
3. **現状との反実仮想を示す。** 「旧ルールではなぜ難しい／成立しないか」「新ルールで何が可能になったか」を具体的に示す。
4. **新規性・変革性・価値・実現可能性を混同しない。** 斬新な変革でも無価値なら採用しない。未調査の案に「史上初」を付けない。
5. **評価を一時保留して生成し、後から厳格に評価する。** 生成中に早く結論を出さない。生成量は必要最小限に抑える。
6. **独立した発想経路を確保する。** 同じアイデアの言い換えを複数案と数えない。
7. **説明は判断に必要な根拠だけ。** 内部の長い思考過程を延々と記述せず、変更した規則・得られた案・評価の要点を示す。

## 起動時の設定

ユーザー指定があれば従う。なければ次を採用する。

- **Mode = standard**：概念空間をモデル化し、異なる系統のオペレーターを3つ、候補6〜9案、推奨案1つを提示。
- **quick**：2オペレーター、候補4案、優先案1つ。短い回答を求められた場合。
- **deep**：4〜5オペレーター、候補8〜12案、上位3案を比較。深掘りや本格企画。
- **research**：deepに加え、利用可能な調査ツールで既存の類似事例を確認。調査不能ならその旨を明記。
- 分野、対象ユーザー、制約、評価軸が不明でも、非破壊的で明示可能な仮定を置いて進める。重要な制約がない限り質問で止めない。

## 手順

### 1. 問題を定義し、現在の概念空間をモデル化する

短く次を整理する。

- **意図**：何のための創造か。楽しさ／驚き／表現力／使いやすさ／収益など。
- **守る条件**：ユーザーが明示した必須条件（Hard constraints）。改変しない。
- **暗黙の規則**：そのジャンルで当然とされるルールを4〜7個。
- 規則ごとに `確定された条件 / 業界慣習 / 推測` を区別。資料がない業界慣習は断言しない。
- 「この規則のままでは考えにくい、または不可能な案」を1〜2個特定する。

規則の候補：`主体は誰か / 何を入力するか / 何が出力か / いつ起きるか / 誰が制御するか / 因果の向き / 成功とは何か / どこに体験があるか / 何を固定するか`。

### 2. 適切なオペレーターを選択する

詳細は必要に応じて [references/OPERATORS.md](references/OPERATORS.md) を読む。標準では**異なる系統を最低2つ**用いる。

| 状況 | 第一候補 | 操作 |
| --- | --- | --- |
| 前提が強く固定されている | `ASSUMPTION_SHIFT` | 前提を否定・反転・移動する |
| 解くべき問題そのものが怪しい | `PROBLEM_REFRAME` | 問題の表現・目的・単位を変える |
| 両立できない要求がある | `CONTRADICTION`（TRIZ） | 妥協せず矛盾を分離・解消する |
| 似たアイデアばかり出る | `STRUCTURAL_ANALOGY` | 異分野の構造を転用する |
| 既存の表現に閉じ込められる | `CONSTRAINT_REWRITE` | 生成規則として制約を付け替える |
| 組合せの探索不足 | `RELATION_RECOMBINE` | 要素ではなく関係を組み替える |
| 奇妙な観察・問題がある | `ABDUCTIVE_LEAP` | 観察を説明する別の仕組みを仮定する |
| 評価の仕方が新しさを阻む | `VALUE_SHIFT` | 成功や価値の関数を変える |

### 3. **規則の変形** → **新しい空間の探索** を別々に実行する

各オペレーターについて、簡潔に記録する。

```text
old_rule: 変更前に当然とされていた規則
operation: 選んだ操作と何を変更したか
new_rule: 変更後の規則（単なる形容詞の追加は不可）
new_possibilities: 旧ルールでは成立しにくかった可能性2つ以上
cost_or_tradeoff: 新たに失うもの・増える課題
ideas: 新ルールから自然に導かれる具体案2〜3個
```

- **変更箇所がルールではなく見た目・名称・ジャンル混合だけ**なら、変革案と呼ばず探索的／組合せ的な案に分類する。
- アイデアを単に反転して破綻する場合、成立する条件を探す。必須条件は破棄しない。
- 異なるオペレーターから出た案でも、根底のルール変更が同一なら一つの経路にまとめる。

### 4. 評価する

詳細は必要なら [references/EVALUATION.md](references/EVALUATION.md) を読む。候補を次の軸で**各0〜3点の暫定評価**を付ける。

- **T（変革性）**：旧ルールでは生成しにくく、新ルールによって初めて成立するか。
- **V（価値）**：ユーザーの目的や体験に具体的な利点があるか。
- **C（成立性）**：内部矛盾がなく、指定制約内で成立するか（実装可能性と芸術的説得力は分野に応じて判断）。
- **D（多様性）**：ほかの候補とは異なる概念空間を開いているか。

点数は主観的な作業用ヒューリスティクスであり、客観的測定値ではない。合計点だけで順位を決めない。**Tが2未満なら「変革的」と宣言しない**。VやCが低ければ意図的な実験案として残すか、改善する。世界初かどうかの新規性判定は別タスク。

少なくとも1案には次の反証を試みる：
- 旧ルールを変えなくても実現できないか？
- 別名を付けただけではないか？
- 一番大切な楽しさ／有用性を壊していないか？
- 既知のジャンルの単純な移植ではないか？

T>=2の案が1つもなければ、**一度だけ**別系統のオペレーターに切り替えてやり直す。それでも駄目なら「今回は探索的な発想に留まった」と明記し、無理に革新を装わない。

### 5. アイデアを届け、すぐ試せる形にする

ユーザーが指定した成果物・文体を優先する。指定がない場合は以下の最小フォーマットを使う。

1. **出発点**：守る条件／今回疑った旧ルール（3〜5行）。
2. **発想の分岐**：異なる原理で生まれた上位3案を、`旧ルール → 新ルール → 体験の核` で各2〜4行。
3. **推奨案**：一番有望な案を具体化。誰が何をすると何が起きるかを説明。
4. **変革性の根拠**：旧規則の下では何ができなかったか、新規則でどのような設計が生まれるか。
5. **代償と最小実験**：弱点1〜2点、短時間で価値を確かめられる試作・問い1つ。
6. **未検証事項**：類似事例や技術実現性を調べていなければ明示。

深い依頼では上位案の比較表を追加。軽い依頼では短く。ユーザーが1案だけを要求したら1案だけにする。追加の文献解説は要求された場合のみ行う。

## 調査と根拠の扱い

- アイデア生成は外部調査なしでも行える。**ユーザーが「世界初」「国内でまだない」「特許」「競合」を気にする場合は調査し、既存例との違いを示す。**
- 調査結果と推測は区別する。閲覧できなければ既知かどうか判断しない。
- 参照資料を引用する場合は、原典の主張とこのスキルの手順を区別する。
- 私的情報を外部に送らず、調査が必要なら機密を一般化した検索語を使う。
