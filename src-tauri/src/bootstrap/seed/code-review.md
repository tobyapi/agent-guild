# コードレビューの観点（保守性・凝集度・テスト容易性）

## 0. まず全体像
- 変更の目的を1文で言えるか。説明と実装がずれていないか
- 影響範囲（呼び出し元・データ・設定・公開している契約）を把握してから細部を見る

## 1. 責務と凝集度
- 1つの関数・モジュールが、1つの理由でしか変わらない形になっているか
- 名前を見れば中身が分かるか。manager・util・helper・data のような曖昧な名前に注意
- 関数は短く（目安60行まで）、分岐は浅く（ネスト3段まで）

## 2. 依存と結合度
- 依存の向きは内側（ドメイン）へ向いているか。I/O や外部サービスはインターフェース越しか
- グローバルな状態・シングルトン・隠れた副作用はないか
- 1つの変更が多くのモジュールに波及していないか

## 3. テスト容易性
- 純粋なロジックが I/O から分かれていて、単体テストできるか
- 時刻・乱数・ID・ファイルシステムはテストで差し替えられるか
- 失敗する経路（エラー・空・境界値）のテストがあるか

## 4. 正しさと堅牢さ
- エラーを握りつぶしていないか。使用者に見せるメッセージは次の行動が分かるか
- 境界値（0件・1件・最大）、文字コード、タイムゾーン、並行実行
- panic・無限ループ・リソースの解放漏れ・ロックの持ちすぎ

## 5. 返し方
- 冒頭に判定を1行: ✅ 問題なし / ⚠️ 要修正 / ❌ 作り直し推奨
- 指摘は「必須」「推奨」「好み」に分け、必須から書く
- 直し方は小さなコード片で示す（全部を書き直さない）
